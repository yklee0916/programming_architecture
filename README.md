# 2_procedural_separation

## 개요

이 브랜치는 절차적 분리(Procedural Separation)를 적용한 개선된 코드를 보여줍니다. `LoginActivity.java`의 모든 로직을 함수/메서드로 분리하여 가독성과 유지보수성을 향상시켰습니다. 하지만 여전히 Activity에 강하게 결합되어 있고, 객체지향 설계 원칙을 완전히 따르지 않는 한계가 있습니다.

## 현재 코드 상태

### 파일 구조
- `LoginActivity.java`: 메서드로 분리된 로직들

### 코드 특징
- **메서드로 분리된 로직**
  - `setupUI()`: UI 구성
  - `setupLoginButton()`: 로그인 버튼 설정
  - `validateInput()`: 입력 검증
  - `performLogin()`: 로그인 수행
  - `sendLoginRequest()`: 네트워크 요청
  - `handleLoginResponse()`: 응답 처리
  - `saveUserData()`: 데이터 저장
  - `navigateToMain()`: 화면 전환

- **간결해진 `onCreate()`**
  - 125줄 → 3줄로 단축
  - 메서드 호출만으로 구성

- **여전히 남아있는 문제들**
  - 예외 처리 부족 (포괄적 Exception 처리)

## 1_spaghetti_code 대비 개선된 점

### 1. 가독성 향상
- **개선**: 125줄의 긴 메서드가 여러 개의 작은 메서드로 분리됨
- **효과**: 
  - 각 메서드의 역할이 명확해짐
  - 코드 흐름을 이해하기 쉬워짐
  - 새로운 개발자가 코드를 빠르게 이해할 수 있음

### 2. 유지보수성 향상
- **개선**: 기능별로 메서드가 분리되어 수정 범위가 명확해짐
- **효과**: 
  - 에러 메시지 변경 시 `showError()` 메서드만 수정하면 됨
  - 검증 로직 변경 시 `validateInput()` 메서드만 수정하면 됨
  - 작은 변경이 다른 부분에 영향을 주지 않음

### 3. 코드 재사용 가능성 향상
- **개선**: 일부 메서드가 독립적으로 사용 가능
- **효과**: 
  - `validateInput()` 메서드를 다른 화면에서도 사용 가능
  - `showError()` 메서드를 다른 에러 표시에 재사용 가능
  - 공통 로직의 중복 제거 가능

### 4. 디버깅 용이성 향상
- **개선**: 각 기능이 메서드로 분리되어 문제 발생 지점 파악이 쉬워짐
- **효과**: 
  - 스택 트레이스에서 문제가 발생한 메서드를 바로 확인 가능
  - 각 메서드에 브레이크포인트를 설정하여 디버깅 가능
  - 버그 수정 시간 단축

### 5. 협업 용이성 향상
- **개선**: 메서드 단위로 작업 분담 가능
- **효과**: 
  - 여러 개발자가 동시에 다른 메서드를 수정 가능
  - Git 충돌 가능성 감소
  - 코드 리뷰가 용이해짐

### 6. 부분적 테스트 가능성
- **개선**: 일부 메서드가 독립적으로 테스트 가능
- **효과**: 
  - `validateInput()` 메서드는 독립적으로 테스트 가능 (Activity 의존성 제거 시)
  - 정적 메서드로 변경하면 더 쉽게 테스트 가능

## 여전히 잔재하는 단점

### 1. Activity에 강한 결합
- **문제**: 모든 메서드가 Activity의 인스턴스 변수와 메서드에 의존
- **영향**: 
  - 단위 테스트 작성이 여전히 어려움 (Activity 컨텍스트 필요)
  - 다른 화면에서 로직을 재사용하기 어려움
  - Activity 생명주기와 강하게 결합됨

### 2. 책임 분리 부족 (여전히 SRP 위반)
- **문제**: 하나의 클래스가 여전히 여러 책임을 가짐
  - UI 렌더링 (`setupUI()`)
  - 사용자 입력 검증 (`validateInput()`)
  - 네트워크 통신 (`sendLoginRequest()`)
  - 데이터 저장 (`saveUserData()`)
  - 화면 전환 (`navigateToMain()`)
- **영향**: 
  - 각 책임을 독립적으로 테스트하거나 개선하기 어려움
  - 레이어 분리가 없어 확장성이 제한적

### 3. 예외 처리 부족
- **문제**: 
  - 모든 예외를 `Exception e`로 포괄적으로 처리
  - 구체적인 에러 정보가 사용자에게 전달되지 않음
  - 네트워크 오류와 기타 오류를 구분하지 않음
- **영향**: 
  - 디버깅이 어려움
  - 사용자에게 적절한 피드백 제공 불가

### 4. 테스트 가능성 제한
- **문제**: 
  - 여전히 Activity 컨텍스트에 의존
  - 네트워크 호출을 모킹하기 어려움
  - SharedPreferences 접근을 모킹하기 어려움
- **영향**: 
  - 단위 테스트 작성이 어려움
  - 통합 테스트에 의존해야 함

### 5. 확장성 부족
- **문제**: 
  - 새로운 로그인 방식 추가 시 기존 메서드 수정 필요
  - 소셜 로그인 추가 시 코드가 복잡해짐
  - 다양한 인증 방식 지원이 어려움
- **영향**: 
  - 기능 확장 시 코드 복잡도 증가
  - 유지보수 비용 증가

### 6. 의존성 주입 부재
- **문제**: 
  - 모든 의존성이 하드코딩되어 있음
  - 네트워크 클라이언트, 저장소 등을 주입받지 않음
- **영향**: 
  - 테스트가 어려움
  - 구현을 교체하기 어려움
  - 모킹이 어려움

### 7. 레이어 분리 부재
- **문제**: 
  - Presentation, Domain, Data 레이어가 분리되지 않음
  - 모든 로직이 Activity에 집중됨
- **영향**: 
  - 비즈니스 로직과 UI 로직이 섞여 있음
  - 아키텍처 확장이 어려움
  - 코드 재사용이 제한적

## 참고

이 코드는 절차적 분리를 보여주는 교육 목적의 예제입니다. 실제 프로덕션 환경에서는 더 나은 아키텍처 패턴을 적용해야 합니다.
